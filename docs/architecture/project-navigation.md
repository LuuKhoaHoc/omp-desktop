# Project navigation (#27)

Tabs are grouped by **project = (profile, folder)**: `src/app/project-nav.js` (`window.OMP_PROJECT_NAV`, regression `test-project-nav.mjs`) is the single definition, shared by the tab bar (`design/tab-group-chip.jsx` renders a group of ≥2), the sidebar (`design/project-sidebar.jsx`), the history panel's per-project filter chips (`sessionProjects`, #35 — saved sessions are already one profile's, so the folder alone is the key) and `live.js`'s focus-existing lookups. Paths compare via `normPath` (slashes, trailing slash, case only for Windows drive/UNC paths); pathless tabs never group.

- **Tab bar presentation.** The strip is on by default (tweak `tabBar`; the earlier `tabStrip` key is dead: every stored copy held its old `false`). A project with ≥2 tabs is a `TabCluster` (`tab-group-chip.jsx`): a head with the folder name (click: `groupTarget`'s pick, i.e. the active member or else the newest; drag: the project), then one tab per conversation in `membersNewestFirst` order (title only, "new conversation" while it still carries the folder's name; run dot, number, ×, double-click to rename, middle-click to close, drag within the project) and a "+" for another conversation in it. A single-tab project is a plain tab labelled by `TabLabel` (`tab-group-chip.jsx`, also used by the sidebar's single-tab row) from `tabLabel` (#46): `folder · title`, the folder truncating first, without a prefix while the tab's name is still its folder name. The prefix is derived, never part of the renameable `name`. Tabs keep their width and the strip (`.tabs-scroll`) scrolls sideways, with the tab in front scrolled into view a frame after it changes; the strip's own "+" menu sits outside the scroller, which would clip it.
- **Member order.** The chip dropdown and the sidebar's expanded rows list members in reverse registry order (`membersNewestFirst`, #38), so a newly opened conversation comes first. Display only: `sessionRegistry` keeps opening order (or the dragged one, below), which `groupTarget`, `open-tabs.json` restore and `closeSession`'s next-active choice read.
- **Keyboard order and tab numbers.** `OMP_PROJECT_NAV.listedTabs` is the one order the keyboard counts in: projects in tab-bar order, each project's members newest first, i.e. the sidebar's rows top to bottom. `desktop.tab.goto1`…`goto9` (Ctrl+1…9) and next / previous tab (`OMP_SETTINGS_TAB.cycle` in `app-live.jsx`) both use it; before, they counted in registry order, which the sidebar shows reversed inside a project. `tabDigits` gives each of the first nine tabs its number and `groupDigits` a project's range (`3–5`) for a folded sidebar project or a tab-strip chip. `TabNumber` (`tab-group-chip.jsx`) renders them in the sidebar rows, the strip's tabs and chips, and the chip dropdown, hidden until `<html>` has `show-tab-numbers`: `useTabNumberHint` (`app/use-keymap.jsx`) sets it 220 ms after the modifier of a bound go-to-tab chord goes down (`OMP_KEYMAP.tabNumberModifiers`: Ctrl by default, derived from the bindings) and clears it on release, on a key that makes it another shortcut (`tabNumberStep`) and on window blur. A class, not state: holding Ctrl re-renders nothing. A project's tab count hides while its range shows.
- **Reorder (#40).** Drag a project along the tab bar or the sidebar, or a conversation within its project in the chip dropdown or the sidebar; `Ctrl+Shift+PageUp`/`PageDown` (`desktop.tab.moveLeft`/`moveRight`) move the active tab's project one place. `OMP_PROJECT_NAV.moveGroup`/`moveMember`/`shiftGroup` compute the new tab order — every project contiguous, which `groupTabs` renders the same — and `OMP_BRIDGE.reorderTabs(ids)` rebuilds `sessionRegistry` in it, applying only an exact permutation of the open tabs (a stale snapshot is a no-op); `notify` then persists it to `open-tabs.json`, so the order survives a restart. A member drop is in display order, the registry's reverse: a drop above a row is a registry move behind it (`handleReorder` in `app-live.jsx`). Since the registry order is the order, a dragged member to the top of a list is also what a click on the chip and `findProjectTab` pick, and `closeSession` hands focus to the registry's last tab as before.
- **Drag mechanics** (`design/ui/use-drag-reorder.js`, geometry `app/drag-reorder.js`): pointer events, not HTML5 drag and drop — chosen while Tauri's native file drop (`dragDropEnabled`) still swallowed HTML5 drag events on Windows; it is on again in this fork (the composer's `@path` drop), and pointer events stay for the threshold, Escape and capture. Items carry `data-reorder-list/-id/-axis`; only items of the pressed one's list are targets, so a member never lands among projects. A press becomes a drag after 5 px, so a click still selects; the click a drop produces is swallowed, Escape cancels, and the pointer is captured on the item. Controls inside an item (×, ▾, rename, an inline input) and a `data-no-reorder` region (the chip's dropdown, outside its rows) never start a drag. `.tabs` is outside `.chrome`, so a tab drag never reaches the window-drag handler.

- Recent projects live in `<app config>/recent-projects.json` (`src-tauri/src/recent_projects.rs`), one list keyed per entry by profile, capped at 20 per profile, newest first. Disposable data: an unreadable file reads as empty and the next write replaces it; entries whose folder is gone are hidden, not deleted. Without an app config folder the list lives in memory for the app run (no temp-dir fallback, see `session-model.md`). `recent_projects_touch` canonicalises (`external_open::canonical_folder`), and so does `open_project`'s folder picker — tab paths and recent entries must be in the same form, or a folder picked through a symlink would not match its open tab.
- `live.js` records a recent only after a successful spawn (`_startProjectSession`, and a profile switch's respawn), and keeps `recentProjects` for the *active* profile only (`_syncRecentsProfile` on activation, last-tab close, profile refresh). All recents IPC runs through one queue (`_recentsCall`): the backend's `list` is unlocked, so unordered calls could let a stale list overwrite a newer touch.
- `openSession`/`+`/`Ctrl+T` always spawn. `openProject` (a recent row) and `resumeSession` focus an existing tab first (`findProjectTab` / `findConversationTab`). The latter matches the registry's `sessionFile`, seeded with the resume path and refreshed from `get_state` while the tab is active; `/new` and a profile respawn clear it (`_freshConversationFields`).
