# Subagent manager

Replaces the old prototype-only "peer session" split/rail widgets (removed). omp streams subagent activity over RPC once subscribed: `set_subagent_subscription` (`off | progress | events`), frames `subagent_lifecycle` / `subagent_progress` / `subagent_event`, plus `get_subagents` (running agents only) and `get_subagent_messages` (tails an agent's session file by byte offset). `src/app/subagents.js` is the pure reducer over those frames (regression: `test-subagents.mjs`); `live.js` keeps its result in `state.subagents`, snapshotted per tab like the transcript.

- omp's registry *deletes* an agent on its terminal status, so the desktop keeps finished agents itself until the session changes (`_resetSessionVars`). Don't replace the local copy with `get_subagents`.
- `_initFetch` re-asserts the subscription (a respawned process starts at `off`) and calls `get_subagents` on every activation — but drops its post-negotiate batch if a tab switch started meanwhile (`_switchGen`), since it would still address the tab being left; `mergeSnapshots` marks agents that were live locally but are no longer listed as ended with `unknownOutcome` (finished outside the journal replay window).
- A dead process (the `agent://exit` listener, or a startup error surfaced on activation) ends its live agents via `mergeSnapshots(…, [])` — nothing else ever would.
- Receive time is not start time: journal-replayed frames arrive late, so `applyProgress` pulls `startedAt` back to `now - progress.durationMs`.
- `events` is the expensive level: only while an agent the manager actually holds is on screen in the inspector (`useSubagentManager` derives `inspecting` from the resolved agent, not the raw id → `OMP_BRIDGE.setSubagentInspecting`). `_switchToSession` downgrades the process being left before `activeSessionId` moves, but leaves the flag to the UI.
- The Rust bridge only forwards allowlisted command types (`ALLOWED_COMMAND_TYPES` in `src-tauri/src/agent/mod.rs`) — a new RPC command in `live.js` must be added there too, or `send_command` rejects it before it reaches omp.
- The manager pane *is* the `layout: "split"` column (`.window.is-split`, the `layout` tweak, also Settings → Layout); open/close goes through `setTweak`. Transcripts (`state.subagentTranscripts`) are ephemeral — not snapshotted, dropped on tab switch, refetched on demand; a response landing after a switch is discarded.
- Running marks are static: `.sa-dot.running` and `.sa-tool.running` (`layout/subagents.css`) carry no animation. Three live agents kept about a dozen `pulseDot` loops going, each one compositing for as long as it ran; the elapsed clocks already show that an agent is alive. Generic status dots across the desktop UI (`styles.css`, `chrome.css`, `chat.css`) are now static too (aside from widget attention marks, which keep their contract). The agent's model (`progress.resolvedModel`, through `saModelName`) is the last item of a row's foot, which wraps so a narrow pane puts it on its own line instead of cutting it.
- **Steer and stop** (`design/subagents/subagent-controls.jsx`, live only while the inspected agent is `running`; after that it stays only to hold text that never got through): the message box sends on the Settings → Composer send key (`isSubmitKey(e, submitKey)`, passed down from `app-live.jsx` through `SwarmPane` and `SubagentInspector`). `OMP_BRIDGE.steerSubagent` sends `steer_subagent`, `cancelSubagent` sends `cancel_subagent`, both id-correlated. omp runs a steered message through the subagent's own `prompt()` (slash commands and templates run *inside* the agent, no images) and holds the reply until the agent accepted it, so a timeout is reported as "may still arrive", not as a refusal. The message reaches the event stream as a `user` `message_end`; `summarizeEvent` shows only `attribution: "user"` ones — the task prompt and omp's reminders are `agent`-attributed. A stop is confirmed in place first; `cancelled: false` means the agent was no longer running, and the record ends with omp's `aborted` lifecycle frame, never locally.

## Messages tab (agent-to-agent IRC) and `/swarm`

Measured on omp 18.20.0 (a `task` batch of two agents, `Alpha` messaging `Beta` with `write agent://Beta`, run through `rpc-ui` at subscription `events` and again at `progress`; the relay frame arrived at both):

- Every agent-to-agent message reaches the main session as a top-level frame `{ type: "irc_message", message: { role: "custom", customType: "irc:relay", details: { from, to, body }, timestamp, … } }`. It is not gated by the subagent subscription level.
- The recipient's copy is a `subagent_event` whose event is an `irc_message` with `customType: "irc:incoming"` and `details: { id, from, message }`. It repeats the relay, so the reducer ignores it.
- Not measured: a message from the main agent to a subagent (omp wraps it as a steering `<irc from="parent">` user message, [omp #18073](https://github.com/can1357/oh-my-pi/issues/18073)), and `agent://all` broadcasts (main agent only). Neither is known to produce a relay frame.
- `app/subagents.js` `applyIrc` keeps relay frames in `state.subagents.board` (newest 500; a replayed frame with the same stamp, sender, recipient and body is dropped). `put` spreads the old state, so agent updates keep the board. `live.js` routes `irc_message` beside the three `subagent_*` frames.
- The pane (`design/subagents/swarm-pane.jsx`, the `.split` column; its Full view button, or Escape to leave, makes it cover the stage) has three tabs, **Board / Members / Graph**, over that state; it opens on Board once there is a post, else Members.
- **Board** (`subagent-board.jsx`): a search box (`searchBoard`), a Filter button that reveals one chip per member, a "New" divider before the first post after the count the pane saw when the tab was last left (`seen`), Follow (on by default, off once the feed is scrolled up). Each post is a flat row (no card): the sender's tile (`swarm-bits.jsx` `SwarmAvatar`, initials on a tint of `agentHue`), `@sender → @recipient`, `#n · h:mm AM` (no seconds), then the text clamped to three lines with a fade and Show more. `SwarmBody` renders `` `code` `` as a chip and `#n` as a button that jumps to (and flashes) post n when it exists; the split lives in `app/swarm-view.js` `bodyTokens` (tested in `tests/test-swarm-view.mjs`) and the text is never HTML. An empty board says why (no agent has messaged another yet) instead of the filter message.
- **Members** (`swarm-members.jsx`): a Coordinator row first (a board name that is not an agent: the main agent; shown even before any agent is registered), then `membersByGroup`: running/pending is Active, `completed` is Finished, `failed`/`aborted` is Stopped. A row is the tile with a status dot, `@name`, the state word, the model, the task description, and `lastPostOf` (the newest post it sent or received); the agent kind shows in the footer only when it is not `task`. omp has idle and parked agents (revived by a message, [tools/task.md](omp://tools/task.md)), but no RPC frame or `get_subagents` snapshot carries those states: captured lifecycle/progress statuses are only pending/started/running/completed, `get_subagents` lists running agents only, and `steer_subagent` refuses a finished one. So there is no Antigravity-style "Standing by" group; adding one needs omp to expose the state.
- **Graph** (`swarm-graph.jsx`): `boardEdges` (directed pair → count, self-posts skipped) on an ellipse layout (`layout` shrinks the horizontal radius so the widest pill stays inside the canvas); the replay bar (top) re-derives the edges from the first N posts. Under it: "N/M posts over T", a **Hide silent members** switch (members with no post yet at the replay step; the RPC has no idle state to base "inactive" on), Even / Real-time pacing and a 0.5x to 4x speed (`OMP_SWARM_VIEW.playDelay`). A node's dot is filled while the agent runs and a ring while it has posted nothing. "Expand @all" is not built: omp sends no broadcast frame.
- **Motion** (all off under `prefers-reduced-motion`; the repo's rule is no looping pulses on status dots, so none are added): a post that arrives while the Board is open rises in once (`.sw-post.fresh`: posts past the count at mount). In Graph, a post that appears (a replay step forward or a live arrival) sends one pulse (`SwarmPulse`): a dot rides the arrow's curve (`curve().at(t)`, 700 ms) and a ring opens on the receiver, written straight to the SVG nodes in a `requestAnimationFrame` loop that ends with the pulse. Every member's avatar is a pixel-art bee like Antigravity's tiles (`app/swarm-mascot.js` `sprite`/`draw`, `swarm-mascot.jsx`): a 16 x 16 grid of squares on a 2-D canvas (no three.js, no image files), side view with the head to the left, body in the member's `agentHue` (a `var(--x)` is resolved from the computed style, a canvas cannot) with two bands, a big eye, a stinger and a grey-white cloud of wings; the ink and wing colours are fixed, so the bee reads the same on every theme. The coordinator is amber with a gold crown. Squares are whole device pixels (the canvas scale is read from the context), so edges stay sharp at any size. A bee swaps two wing poses (150 ms each, dipping one row in the down pose) only while its agent is running (Members tab) and reduced motion is off; otherwise it is one still frame. All beating bees share one loop (`createBeat`): after each draw it waits 50 ms on a timer and only then asks `requestAnimationFrame` for the next frame (no frame callbacks in between). It stops with the last bee, and when it wakes with the page hidden it goes to sleep (no timer, no frame request) until `visibilitychange` calls `resume()`. The `prefers-reduced-motion` change is listened to, so it takes effect without a remount. A worker whose hue hashes to amber looks like the coordinator apart from the crown.
- `/swarm` is an omp file command, `examples/commands/swarm.md`, and the app installs it: `bundled_commands.rs` embeds the file (`include_str!`) and `start_session` writes it to `<omp agent dir>/commands/swarm.md` of the tab's profile (`profiles::agent_dir_for`: `~/.omp/agent/` for the default profile, `~/.omp/profiles/<name>/agent/` for another) before omp starts. A file already there is never overwritten, so an edited command stays; a deleted one comes back on the next tab start. A failed write is logged and never stops the tab. omp lists the file in `get_available_commands`, so the palette shows it and omp expands it; a desktop command of the same name would shadow it, so none exists. Coordinator brief over omp's `task` tool and `write agent://<name>`.
- omp's side, from its docs (not its roadmap): an idle or parked agent costs no tokens until a message revives it (`write agent://<id>`), a spawn can pick a model (`task.perCallModel`) and a revived agent keeps its saved one, `WATCHDOG.yml` advisors review a session. The docs describe no swarm monitor and no model change for a live agent.
